# C-07 — the empty DFly2 context pass: closed without code

The item, as opened on issue #95:

> #### C-07 Empty DFly2 context pass still costs a barrier round
> - Area core (additive export) · PL · Gain DFly2: 2 barrier rounds a step (~5-20 us) · Conf medium · Effort S-M
> - Change: `hyv4flash.cpp:1113-1119` (`draft_pass < 0` issues nothing); kernels/dfly2.md §3.5 point 1 /
>   §9 item 5: a core export that drops the empty pass (`engine_draft.cpp:1038-1041`).

**Closed, without code, on the numbers.** The pass is real and it is empty: every boot of the base arm
records `draft pass -1` with 0 records and 0 dispatches, and no boot of the branch records that pass at
all — so the change does what it claims at the call site. It just does not make the step faster. The
1,156-record decode pass goes 29.617 → 29.689 ms and the 298-record short pass 4.701 → 4.704 ms on the
same machine, a change inside the boot-to-boot noise; the served A/B's +3.9 % c1 aggregate sits inside
the clean rounds' own 100.5–105.6 tok/s spread. CARDS.md §2's second clause — "the kernel, op or step
the item targets is measurably faster in ms" — is not met, and §2 says an unmet bar means this note and
no merged code.

The code is in this branch's history at `0c56f9a2` (`git show 0c56f9a2`) and is reverted by the commit
that adds this note: `git diff cf11ed50 -- . ':(exclude)notes'` is empty, so the tree is `cf11ed50`'s
again apart from the notes.

## What was tried

An additive core export `rad_drafter_no_context_pass(RadBuilder*)`, mirroring `rad_drafter_shared_kv`:

- `abi/rad_builder.h` — the declaration, refusing unless a BLOCK drafter is declared and it is not a tree.
- `core/build/rad_builder.cpp` — `Builder::drafter_no_context()`, with `RAD_E_STATE` refusals for a
  missing drafter, a serial head and a tree (whose context pass stages the accepted path).
- `core/rad_core.h`, `core/build/rad_build.h`, `core/engine.h`, `core/engine_bringup.cpp` — the flag,
  carried from the program into `no_context_` at bring-up.
- `core/engine_draft.cpp` — the guard: `sched_.block_context(step)` still runs, the tree staging still
  runs, and only the pass is skipped (`if (!no_context_) RAD_TRY(block_pass(cb, "context", step));`).
- `arch/hyv4flash/hyv4flash_dfly.h` — DFly2 declares it after `rad_drafter_short_block`.
- `tests/build_test.cpp`, `tests/arch_fakes.h`, `tests/hyv4flash_arch_test.cpp` — the declare-side
  test `a_block_head_with_no_context_pass_declares_it` (nothing declared / serial head / block / tree)
  and the arch test's call-site assertion.

Two findings from the review stand and are recorded here for the reopen:

- **The tests cover only the declare side.** No test fails without the engine change: the four-case test
  passes on both trees because it exercises the export's refusals, not the skip, and the arch test only
  asserts that the call site is there. The engine behaviour — the context pass not running when
  `no_context_` is set, and the snapshot saved right after it still carrying what the step needs — has
  no test at all. That gap is blocking for a code change and is part of why this closes without one.
- **The header comment cited the wrong section.** `abi/rad_builder.h` said `kernels/dfly2.md §3.5 point 2`
  where the issue cites `§3.5 point 1 / §9 item 5`; the file is no longer in this diff, so the finding is
  moot for the closure but should be fixed if the change is ever reopened.

**These are two different passes, not a before/after of one.** `draft pass 1` (298 records, the short
block) is 4.701 → 4.704 ms; `draft pass 0` (1,156 records, the decode block) is 29.617 → 29.689 ms. The
earlier PR text that set 4.701 against 29.617 as a before/after is wrong and is retracted here.

**The removed pass cannot appear in this table.** The base arm's boot log records it as a pass with no
records at all:

```
$ grep 'recorded pass' base-boot.log | head -3
I recorded pass: draft pass -1 at 68 token(s) -- 0 records, 0 of the 0 dispatches unordered behind the one before; 0 host op(s), 0 table refresh point(s) and 0 routing report(s) between the played stretches
I recorded pass: draft pass 1 at 6 token(s) -- 298 records, 53 of the 298 dispatches unordered behind the one before; 0 host op(s), 0 table refresh point(s) and 0 routing report(s) between the played stretches
I recorded pass: draft pass 0 at 3 token(s) -- 1156 records, 361 of the 1148 dispatches unordered behind the one before; 4 host op(s), 328 table refresh point(s) and 41 routing report(s) between the played stretches
```

`stampgaps.py` groups by records, so a pass with 0 records is not a group it can differ on. What the
change removes is two host barrier rounds, and those are not stamped dispatches either. That is the
whole explanation of the null: the term the item targets is below this table's resolution, so this run
could not have supplied §2's "measurably faster" even if the change were a pure win.

**DFly2 and the change were exercised.** The review could not tell this from the diff, so the run's own
logs are quoted: all four base boots and all four branch boots log
`I speculation: 'dfly2' proposes 5 token(s) in ONE block pass over 6 row(s)` and
`I block drafter 'dfly2' coupled LIVE: 5 position(s), … DFly2 along its chain`; all four base boots then
record `draft pass -1` (0 records, 0 dispatches), and none of the four branch boots does. The context
pass exists, is empty, and is gone on the branch. (In the other window's log, `measure-window-20261125`,
the same pass is recorded at 1,984 tokens as well as 68, also with 0 records.)

That answers the doubt about whether DFly2 ran; it does not rescue the measurement. The null is still a
weak null: one boot per arm for the stamps, no container, not a §1 lane, and no per-pass timing of the
two barrier rounds — so the honest verdict is "not measurably faster on this rig", not "proven free".

## What would reopen it

1. **A §1 lane run**: the u3 container (`hy4-flash-iqr-v4-u3.rad`), 210 W read back on both cards, a
   DFly2 config (`coupled03.yaml`), and **three interleaved boots per arm** (not one), with
   `RADIANCE_AQL_STAMP=1` so the empty context pass is its own group in the CSV: the closure's evidence
   is that `draft pass -1` is present in the base arm and absent in the branch, and at stamp 1 the pass
   count itself is the row to quote. Read `scripts/stampgaps.py` on the neighbouring passes for wall ms,
   and three served rounds for parity and tok/s.
2. **The tests the review named**: one that fails without the change — a fake arch whose block drafter
   keeps no cache, a counter on `block_pass`, an assertion that the `"context"` pass did not run at all,
   and an assertion that skipping it drops no core-side bookkeeping, specifically that the snapshot saved
   right after the context pass (`save_checkpoints`, `core/engine_draft.cpp`) carries the same rows with
   and without the skip.
3. **The change to guard, if it is reopened**: `0c56f9a2` in this branch's history. The header citation
   should then read `kernels/dfly2.md §3.5 point 1 / §9 item 5`, as the issue does.
