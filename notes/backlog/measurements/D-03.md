## What the change is

- `libr4d/r4d_ar_add_rmsnorm.hip` (new): the exact two-rank all-reduce of a block's partial output with the
  residual add and the RMS norm beside it, one kernel, two orders -- `mode` 0 is `all_reduce -> rmsnorm -> add`,
  `mode` 1 is `all_reduce -> add -> rmsnorm`. The fold is `r4d_ar_oneshot_2rank_exact`'s arithmetic (f32 sum of
  the two bf16 halves, one round through `bf16_hi_rne_nan`, stored back into `a` as the standalone all-reduce
  stores it); the add is `add_bf16`'s word and the norm `rmsnorm_bf16`'s, in the same `kR4dSumLanes` partition and
  expression order, so the result is bit-identical at any width and block count. A block owns whole rows, so the
  block count clamps to M. Exact wire only. Built from the junction's AR device functions (`r4d_ar_seq.h`).
- `libr4d/r4d_rows.cpp`: the row (`cArAddRmsNorm` / `tArAddNorm` axes: `nblocks`, `nthreads` 0/256/512/1024,
  `drain`, `acq`), its shape (`a`, `x`, `w`, `y`), its fuse decomposition, and its **schema** -- which the first
  lane boot found missing: the builder refuses an op no loaded plugin declares a schema for (`RAD_E_NOSCHEMA`) and
  the engine stopped at startup with `kernel 'ar_add_rmsnorm' in plugin 'libr4d' implements op 'ar_add_rmsnorm',
  which no loaded plugin declares a schema for`. The schema is `pAddRmsNorm`'s set plus the reduction's: `M` (the
  ranged parameter), `n`, `world_size`, `mode`, `eps`, `dtype`, an optional `w_dtype`, and `wadd` / `mult`
  optional. No card-less test sees this: the emu calls the entry point directly and the arch tests use the
  recording builder, which has no registry.
- `libr4d/r4d_fuse.cpp`: the chain the oracle runs instead of the kernel. Both elementwise steps were wired to
  operand 0 (`a`, the reduced message) instead of 1 (`x`, the stream), so mode 0's add wrote `a` and mode 1's add
  and norm read it: a chain that never touched `x`. Now the kernel's own -- mode 0 `rmsnorm(a) -> y`, then
  `add(x, y) -> x`; mode 1 `add(x, a) -> x`, then `rmsnorm(x) -> y` -- and `a` holds the reduced sum only.
- `libr4d/r4d_shapes.cpp` + `r4d_ar_entry.hip`: the gain's description and the launcher now read one source. The
  shape says f32 unless the geometry passes `w_dtype` (every architecture plugin's norm gains are `RAD_F32`, the
  family note's rule), the launcher takes a bf16 gain only when `w_dtype` says `bf16`, and any other value is
  declined on both sides, so a described buffer and an accepted buffer cannot disagree.
- `arch/hyv4flash/hyv4flash_dfly.h`: both chains declare the twin where the layer has a post-norm, at two ranks,
  untapped, and the library declares the op; `op_post` / `op_add1` / `op_add2` / `op_final*` are cleared where it
  resolved, and `in_norm_done` skips the next layer's input norm (mode 1 writes it). Taps, `world != 2`, an
  undeclared op and a refused launch keep the old chain exactly. The `E: the final norm` block is unchanged:
  that is D-01's `add_rmsnorm`, and where the last layer's mode-1 twin resolves its `op_final` / `op_final_add`
  are cleared by the D-03 loop below it.
- **Scope: the coded write is not done.** The twin writes the plain bf16 stream plane only (`y`, or the next
  layer's `xn` / the final `z`); it has no codes output and no staged (row-block) write -- it owns whole rows,
  the block count clamps to M, and any M the block covers is exact (the emu runs M 1-48). Mode 1 is fused only
  where the next layer's input norm is the plain bf16 norm: a layer whose next input norm is a **codes** norm
  (`op_attn_norm_q`) keeps the chain, and the item's coded write stays open. The served model's draft linears are
  bf16, so every layer takes the twin there; a quantised drafter would take it on its last layer only.
- Tests: `tests/r4d_emu/test_ar_add_rmsnorm.cpp` (both modes against the chain's rows, byte for byte, M 1/3/6/48,
  n 1000-5128, widths 256-1024, one and several blocks, f32 and bf16 gains, the refusals);
  `tests/r4d_fuse_test.cpp` (the chain's ops and wiring in both orders, the chain run symbolically over the four
  operands, the refusals, the gain's description in both dtypes); `tests/hyv4flash_arch_test.cpp`:
  `dfly2_takes_the_fused_reduction_add_norm_where_served_and_the_chain_otherwise` (one layer, all three forms at
  one and two ranks), `dfly2_a_non_last_layers_fused_norm_is_the_next_layers_and_that_layer_issues_none` (two
  layers: layer 0's mode-1 twin takes layer 1's `attn_norm` and writes `dfly.xn`; layer 1 issues no input norm,
  its `q_a` reads the twin's `xn`, its own twin takes the final norm; fails if either half is reverted), and the
  TP2 split test.

### What changed after that commit, and why these numbers still describe this kernel

The review's rule is that the note is the only thing added after the measured commit. That did not hold: the
commits after `86a96fc0` are `88f3fab8` (the two-layer arch test and the `E: the final norm` comment, restored to
the base's text), `9661c758` and `fe568fdb` (this file), and `bb550338` (the chain's wiring, the gain's

## Findings

1. **Parity: identical.** Four greedy prompts, six boots, one `sha256` and one token count for all of them; the
   fused op is the chain's bytes in the served graph, as the emu says it must be. The boot-to-boot instability
   seen later under contention hits the unmodified base arm too (the parity section), so it is not this change.
2. **The op is measurably cheaper in the served pass**: 19 fewer dispatches a draft pass, the families that carry
   the change down 28-32 % (c1) and 20-21 % (c8), the draft pass's exclusive sum down 3.3 % on the c1 round
   medians and 4.9-5.2 % at c8 -- 0.13-0.15 ms of a 3.9 ms pass at c1, 0.24-0.26 ms of a 4.9 ms pass at c8.
3. **e2e: inside noise**, as the item predicts (+0.8 % c1 ms/step, -1.6 % c8 decode step, -2.0 % c8 tok/s, pairs
   of both signs).
4. **The schema gap is the one thing the card-less tests cannot see.** The row, axes, shape, chain and wiring
   were all in place and every test passed; the engine still refused to start on `RAD_E_NOSCHEMA`.
5. **The chain's wiring was wrong and only a test of the chain itself could see it.** The kernel and its emu were
   right; the oracle's chain wrote `a` instead of `x`. `r4d_fuse_test` now holds the wiring and the writes, and
   reverting either the mode-0 add or the mode-1 add/norm fails eight checks.
6. **The item's coded write is not implemented** (scope, not a regression): the twin writes bf16 only, and a codes
   norm keeps the chain.
