## The first boot's fault, and why it does not stand

The 09:55 boot printed `HSA_STATUS_ERROR_EXCEPTION`, `argument +NNN ... in pageable of owner 1 card
1`, and exited 70 — the same signature as `UPSTREAM-REBASE-20261127.md`. The lines above it in the
same journal show the cause: the boot started while the previous engine still held the cards. The
driver had `504.00 MiB` left on each card, W2's `rad_dev_alloc(904.59 MiB)` was refused (`W2 off`),
and the plan was laid out on a card that was already owned. A clean boot — no radiance process, the
cards free — starts and serves: health `ok`, a 48-token decode and a 4,028-token prefill both 200.

The same class is upstream's open #337 / PR #344 (TP2 Hy4 faults in `gemm_i8_kpar_kernel` on long
prompts, no named cause). Nothing here attributes this box's first-boot fault to that: the
contamination is in the journal, and the clean boot has not reproduced it. **Rule this note leaves:
stop `hy4-master`, wait for `pgrep -f 'bin/radiance --config'` to come back empty, and only then
`systemd-run` the next engine.**

## Lever state on this build

* W2 (`core/runtime/w2.h`, upstream default **on**): **off at runtime here** — it asks 904.59 MiB
  and the 262144-token plan leaves 504 MiB a card. The warning says so at startup. Making it fit is
  a budget decision (context, `--gpu-headroom-mib`, host pool), not a switch.
* card 1 settles `146.67 MiB` free against `300.16` wanted: the same squeeze the M-09 measurement
  recorded at the old base. It serves, but the margin is thin.
* `--prefill-span 2` with `--prefill-span-pass piece`: already one routed pass over the step (see
  the note above); the pipeline is off by default (`RADIANCE_HY4_PIPE` unset).
* `RADIANCE_XP_TP2` is present and off; it is the measurement switch, not a served default.
